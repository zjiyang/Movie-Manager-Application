# 电影项目升级记录：做了什么，为什么做

这份文件是项目讲述素材，每完成一步就补一段。已完成的内容才作为经历使用；计划中的内容不算成果。升级过程中使用了 AI 辅助实现，讲述时区分自己提出的需求、理解并验证的决定，以及工具完成的代码。

## 项目是什么

原项目是 CPSC 210 的 Java 电影评分桌面应用，用 Swing 显示界面，用 JSON 文件保存数据。目标是逐步升级为 React 页面、Spring Boot 后端和 PostgreSQL 数据库组成的 Web 应用。

流程：统一构建 → 稳定测试 → 自动检查 → 接入数据库与后端 → 制作网页 → 联调与交付。

## 第一步：让项目有统一的运行测试方式（已完成）

- **用了什么：**Maven，Java 项目的构建和依赖管理工具。
- **之前怎样：**项目已经有 JUnit 测试和本地依赖包，但没有 Maven 配置。
- **改变了什么：**加入 `pom.xml`，声明需要的依赖和源代码位置。可以用 `mvn test` 统一完成编译和测试。
- **为什么这样做：**后面要不断改代码，先建立可重复的检查方式，方便本地和 GitHub 使用相同流程。
- **结果与好处：**当时本地的 25 个测试通过；应用功能没有改变，但构建方式更明确。第一步提交没有包含原来未跟踪的两个事件测试文件。
- **对应提交：**`2ac3c4a`。

## 第二步：让测试更可靠，也不影响项目数据（已完成）

- **用了什么：**JUnit，以及它提供的临时目录功能 `@TempDir`。
- **之前怎样：**一个日期测试要求两次读取的时间完全相同，即使程序正常也可能失败；JSON 写入测试会覆盖项目里的测试数据文件；事件日志是共享的，容易留下其他测试产生的记录。
- **改变了什么：**日期改为检查是否处于创建前后的时间范围；写入测试改用临时文件；事件日志测试前后清理共享记录；补上空数据库读回后仍为空的检查。两个已有事件测试文件也正式加入 Git。
- **为什么这样做：**测试失败应该尽量指向真实问题，而不是运行时机或上一个测试留下的内容。
- **结果与好处：**重新编译后，25 个测试全部通过，项目数据文件没有变化。今后修改代码时，测试结果更值得参考。这一步没有新增电影功能。
- **对应提交：**`fc81eb9`。

### 测试到底是为了什么？

测试就是让程序自动检查事先约定的行为。例如：把电影保存到文件，再读回来，名字、评分和平台信息应该保持一致。以后改成数据库保存时，我们仍然要检查这些行为是否正确。

测试通过表示这批已检查的情况符合预期，不代表程序完全没有问题。例如，平均分的小数和没有评分时的处理仍需要单独补测试和修复。

## 第三步：让 GitHub 每次更新都自动检查（已完成）

- **用了什么：**Maven Wrapper 和 GitHub Actions，也就是基础 CI。
- **之前怎样：**需要在本地手动运行 Maven；GitHub 没有配置自动测试。
- **改变了什么：**用 Wrapper 固定 Maven 3.9.9，以后通过 `./mvnw clean test` 运行；推送代码或提交 PR 时，GitHub 在 Java 11 环境自动编译并运行测试。
- **为什么这样做：**减少漏跑测试，也检查代码在另一台干净的机器上能否正常构建。
- **验证结果：**本地使用 Wrapper 和 Java 11 重新构建，25 个测试通过；修复路径后，GitHub 的 Linux/Java 11 检查也通过。[成功运行记录](https://github.com/zjiyang/Movie-Manager-Application/actions/runs/35821959355)。
- **范围：**这一步检查编译和测试，不包含网页部署，也没有设置“检查失败就禁止合并”的仓库规则。
- **实际遇到的问题：**第一次 GitHub 测试失败。排查发现测试引用的文件名大小写与 Git 中的实际文件名不一致，本地 macOS 没暴露这个问题。修正后 Linux 检查通过，说明换一个干净环境运行测试确实有价值。
- **对应提交：**`61376e5` 添加 CI，`2edc3e9` 修复文件名大小写。

## 第四步：用 Docker 准备 PostgreSQL（CI 验证完成，本地待安装 Docker）

- **用了什么：**Docker Compose、PostgreSQL 17、SQL。
- **之前怎样：**电影存在 Java 对象和 JSON 文件里，没有关系型数据库环境。
- **改变了什么：**增加可统一启动的数据库、电影表和两条演示数据；数据单独放在持久化存储中。电影名不能为空，年份需要在约定范围内。
- **为什么这样做：**为后续 Spring Boot 接入准备存储层，数据库自己也能拒绝不合规则的数据。
- **有什么好处：**启动环境的方式可复现，容器替换后可以继续使用原来的数据。CI 已通过增删改查、输入约束和重建容器后的数据保留检查，原 Java 测试也通过。
- **目前边界：**本机尚未检测到 Docker，本地启动待验证。旧桌面程序仍然使用 JSON，尚未迁移数据，也还没有接入 Flyway；现有建表脚本只在空数据库首次启动时执行。
- **对应提交与证据：**`53e22d9`；[GitHub 检查结果](https://github.com/zjiyang/Movie-Manager-Application/actions/runs/35892767115)。

## 第五步：让接口读到 PostgreSQL 中的电影（CI 验证完成）

- **用了什么：**Spring Boot、Spring Web、Spring Data JPA、PostgreSQL 驱动；后端使用 Java 21。
- **之前怎样：**数据库已经能保存电影，但没有 Web 接口可以读取它，原桌面程序仍使用 JSON。
- **改变了什么：**新增独立后端，通过“电影列表”和“电影详情”接口查询数据库。列表分页返回，电影不存在返回 404，参数不合法返回 400。
- **为什么这样做：**后面的 React 页面需要通过接口取得数据。把页面请求、业务处理和数据库访问分开，方便继续增加功能。
- **有什么好处：**开始打通“请求 → Java 后端 → PostgreSQL → 返回数据”的流程。数据库表保持不变，原桌面版本也保留。
- **验证与边界：**本地编译打包成功，GitHub 上真实 HTTP 与 PostgreSQL 的接口测试通过，覆盖分页、数据更新、无效参数与电影不存在等情况；原 Java 和数据库检查也通过。本机尚缺 Docker；还没有前端、评分写入和登录，Flyway 接管表结构会作为后续独立步骤。
- **对应提交与证据：**`0a7e951`；[GitHub 检查结果](https://github.com/zjiyang/Movie-Manager-Application/actions/runs/35939434260)。

## 已完成部分的讲述素材

我正在把一个 Java 电影评分桌面项目升级成 Web 应用。我先整理了构建和测试流程：用 Maven 统一运行方式，再处理日期测试偶发失败、测试覆盖数据文件和共享日志状态的问题。修改后，25 个测试通过，项目数据也没有被测试改动。这样后面接数据库、改后端时，就有一套更可靠的检查方式。

后来加入 GitHub Actions，让提交后的检查自动运行。第一次在 Linux 上运行就发现一个本地没发现的文件名大小写问题，修正后检查通过。这让我看到，自动测试不仅能检查业务逻辑，也能暴露不同运行环境之间的问题。

接着，我用 Docker 准备了 PostgreSQL，再增加 Spring Boot 查询接口。接口可以分页返回电影，也能区分无效请求和不存在的电影。自动测试通过真实 HTTP 请求和数据库验证这条链路，而不只是检查固定的演示返回值。
